# Выбор и настройка мониторинга в системе

## Мотивация

В текущей архитектуре мониторинг нужен не только для «видимости» инфраструктуры, но и для управления бизнес-процессом. Сейчас компания сталкивается с ростом нагрузки, просроченными заказами, жалобами клиентов и API-пользователей, а также с медленной работой MES. Без мониторинга команда не может быстро понять, где именно возникает узкое место: в API, очередях, базах данных, интерфейсе оператора или в процессе обработки заказа.

Мониторинг даст компании:

- возможность быстро обнаруживать деградации и сбои в онлайн-магазине, CRM и MES;
- прозрачность по состоянию очередей и процессу исполнения заказов;
- раннее предупреждение о перегрузке инфраструктуры до того, как это приведёт к потерям клиентов и контрактов;
- данные для планирования масштабирования и оптимизации производительности;
- более предсказуемый процесс релизов и снижение времени реакции на инциденты.

В условиях роста числа заказов мониторинг становится критически важным инструментом для сохранения качества сервиса и доверия клиентов.

## Выбор подхода к мониторингу

Для разных частей системы целесообразно использовать разные подходы.

- Для API-сервисов: подход RED.
  - R — request rate, количество запросов.
  - E — errors, количество ошибок.
  - D — duration, длительность ответа.
  Это подходит для интернет-магазина, CRM API и MES API, потому что важно отслеживать нагрузку, ошибки и latency пользовательских запросов.

- Для инфраструктуры и ресурсов: подход USE.
  - U — utilisation, нагрузка на ресурс.
  - S — saturation, насыщение ресурса.
  - E — errors, ошибки ресурса.
  Этот подход подходит для инстансов приложений, баз данных и очередей.

- Для бизнес-процесса и производственной цепочки: дополнительно отслеживать ключевые бизнес-метрики и длительность стадий заказа, так как проблемы здесь напрямую влияют на сроки выполнения заказов.

## Метрики и что отслеживать

### 1. API и пользовательские сервисы

#### 1.1 RPS для интернет-магазина, CRM API и MES API
- Зачем: показывает текущую нагрузку на сервисы и помогает понимать, как она растёт по сравнению с планом.
- Ярлыки: service, environment, endpoint, method, client_type.

#### 1.2 Latency API
- Зачем: помогает выявлять медленные запросы и узкие места в обработке. Особенно важно для MES, где страдает работа первой страницы и интерфейс операторов.
- Ярлыки: service, environment, endpoint, method, status_code.

#### 1.3 HTTP 5xx и общий процент ошибок
- Зачем: позволяет быстро выявлять сбои и деградации. Для B2C и API-пользователей это критически важно.
- Ярлыки: service, environment, endpoint, status_code, client_type.

#### 1.4 Количество активных сессий
- Зачем: помогает оценить нагрузку на приложения и выявить резкие всплески использования.
- Ярлыки: service, environment, user_role.

#### 1.5 Объём переданных и полученных данных
- Зачем: полезно для оценки трафика и выявления аномалий в работе API.
- Ярлыки: service, environment, endpoint.

### 2. Инстансы приложений

#### 2.1 CPU utilisation
- Зачем: показывает, насколько загружен процессор и есть ли признаки перегрева вычислительных ресурсов.
- Ярлыки: service, environment, instance.

#### 2.2 Memory utilisation
- Зачем: помогает обнаружить утечки памяти и нехватку ресурсов для приложений.
- Ярлыки: service, environment, instance.

#### 2.3 Количество ошибок процесса / падений приложения
- Зачем: необходимо для контроля работоспособности приложений.
- Ярлыки: service, environment, instance, error_type.

### 3. Базы данных

#### 3.1 CPU и memory utilisation для инстансов баз данных
- Зачем: позволяет понять, что база стала узким местом и требует масштабирования или оптимизации запросов.
- Ярлыки: db, environment, instance.

#### 3.2 Количество подключений
- Зачем: важно для отслеживания роста параллельной нагрузки и риска исчерпания лимитов подключений.
- Ярлыки: db, environment, instance.

#### 3.3 Размер базы данных и рост объёма данных
- Зачем: помогает прогнозировать необходимость увеличения ёмкости и контролировать рост данных.
- Ярлыки: db, environment.

#### 3.4 Время выполнения ключевых запросов
- Зачем: особенно важно для MES и CRM, где медленные запросы в интерфейсе и в обработке заказов напрямую влияют на пользовательский опыт.
- Ярлыки: db, query_family, environment.

### 4. RabbitMQ

#### 4.1 Размер очередей
- Зачем: демонстрирует backlog сообщений и помогает выявлять накопление задач, которое может приводить к задержкам в обработке новых заказов.
- Ярлыки: queue_name, environment, status.

#### 4.2 Number of messages in flight
- Зачем: показывает, сколько сообщений в данный момент обрабатывается и есть ли перегрузка обработчиков.
- Ярлыки: queue_name, environment.

#### 4.3 Number of dead-letter-exchange letters
- Зачем: нужен для выявления сообщений, которые не удалось обработать и ушли в DLQ.
- Ярлыки: queue_name, environment, reason.

#### 4.4 Скорость поступления и обработки сообщений
- Зачем: позволяет оценить, достаточно ли производительности у интеграции и не возникает ли отставание.
- Ярлыки: queue_name, environment.

### 5. Процесс обработки заказов и бизнес-метрики

#### 5.1 Количество заказов в каждом статусе
- Зачем: помогает видеть узкие места в цепочке обработки и понимать, где застревают заказы.
- Ярлыки: order_status, environment, channel.

#### 5.2 Среднее и p95 время нахождения заказа в статусе
- Зачем: критично для контроля SLA и выявления просрочек.
- Ярлыки: order_status, environment, channel.

#### 5.3 Возраст самого старого заказа в очереди
- Зачем: помогает быстро определить, что backlog растёт и есть риск просрочки.
- Ярлыки: environment, channel.

#### 5.4 Время расчёта стоимости изделия в MES
- Зачем: для сложных 3D-моделей это важнейший показатель, от которого зависит время обработки заказа.
- Ярлыки: environment, model_complexity, result_status.

#### 5.5 Количество заказов, которые превысили SLA
- Зачем: напрямую связано с качеством сервиса и удовлетворённостью клиентов.
- Ярлыки: environment, channel, reason.

### 6. UI и фронтенд MES

#### 6.1 Время загрузки страницы и время выполнения запросов дашборда
- Зачем: напрямую влияет на удобство работы операторов и на скорость принятия заказов.
- Ярлыки: page, environment, role.

#### 6.2 Время ответа API-эндпоинтов для дашборда заказов
- Зачем: нужно для анализа узкого места на первой странице MES.
- Ярлыки: endpoint, environment, filter.

## План действий

1. Создать центральную систему мониторинга на базе Prometheus и Grafana, либо использовать управляемые сервисы мониторинга в Yandex Cloud.
2. Добавить сбор метрик из интернет-магазина, CRM API, MES API, RabbitMQ, баз данных и инстансов приложений.
3. Внедрить логирование и распределённое трассирование для ключевых сценариев: создание заказа, расчёт стоимости, передача заказа в MES, переходы по статусам.
4. Настроить дашборды по следующим направлениям:
   - API и пользовательский опыт;
   - состояние очередей RabbitMQ;
   - нагрузка и ресурсы приложений;
   - базы данных;
   - бизнес-процесс заказов и просрочки.
5. Настроить алерты по SLO и критическим порогам.
6. Ввести регулярный процесс анализа инцидентов и улучшения метрик после каждого релиза.
7. Подготовить отчётность по ключевым показателям для бизнеса и поддержки: SLA, количество просроченных заказов, производительность систем и состояние очередей.

## Показатели насыщенности и пороговые значения

| Показатель | Порог насыщения | Почему нужен именно такой порог | Что делать при превышении |
|---|---:|---|---|
| p95 latency API | более 500 мс для интернет-магазина и CRM, более 2 с для MES | Это уже заметно влияет на пользовательский опыт и может привести к росту отказов | Создать alert, проверить узкое место, масштабировать сервис, оптимизировать запросы |
| HTTP 5xx | более 1% запросов в течение 5 минут | Даже небольшой рост ошибок ведёт к потере доверия клиентов и API-пользователей | Открыть инцидент, проверить деплой и последние изменения, при необходимости откатить релиз |
| CPU на инстансе приложения | более 70% в течение 15 минут | Позволяет заранее выявить перегрузку перед тем, как сервис начнёт деградировать | Масштабировать инстанс, проверить узкие места в коде |
| Memory utilisation | более 80% в течение 15 минут | Указывает на риск падения приложения из-за нехватки памяти | Перезапустить сервис, проверить утечки, добавить ресурсы |
| Подключения к БД | более 80% от лимита | База начинает терять устойчивость и рост нагрузки может привести к сбоям | Перенести часть нагрузки, оптимизировать запросы, увеличить лимиты или добавить реплики |
| Размер очереди RabbitMQ | более 1000 сообщений или рост более 100 сообщений/минуту в течение 10 минут | Это знак накопления отставания и риска просрочки заказов | Создать тикет, проверить потребителей, увеличить число обработчиков, при необходимости масштабировать очередь |
| DLQ в RabbitMQ | любое заметное увеличение DLQ | Это указывает на ошибки обработки сообщений и риск потери или задержки данных | Сразу расследовать причину, восстановить обработку, при необходимости вручную переотправить сообщения |
| Возраст самого старого заказа | более 3 дней в очереди | Это уже критичный симптом для бизнеса, потому что заказ начинает просрочиваться | Передать в работу бизнес-операции, вручную перераспределить нагрузку, повысить приоритет |
| Время расчёта стоимости в MES | более 10 минут для типовых моделей и более 30 минут для сложных | Это напрямую влияет на сроки выполнения заказа и на ожидания клиентов | Выделить отдельный alert, проверить производительность расчётов и объём 3D-моделей |

При превышении указанных порогов система должна:

- создавать автоматический alert в системе мониторинга;
- отправлять уведомление ответственным командам в чат или на почту;
- запускать процедуру расследования инцидента;
- при необходимости увеличивать ресурсы, масштабировать инстансы или менять конфигурацию;
- в критических случаях формировать тикет на бизнес-операции и поддержку, чтобы не допустить дальнейшего роста просрочек.
